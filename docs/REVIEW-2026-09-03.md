# dsh-sms 代码评审（2026-09-03，Fable 5.1）

## 结论

- **整体质量高，可以继续在这个骨架上做。** 分层清楚（gmessages 传输 → 监督器 → 会话路由 → 交互代理 → 设置页），fail-closed 原则贯穿始终，64 个测试全绿，构建、审计、打包、rc.8 web profile 安装冒烟全部通过。
- **三个必须修的问题，本次已修并附测试：**
  1. 会话永久死亡（cookie jar 失效 / 手机解除配对）后无限重连，设置页永远显示 "Reconnecting (N)"，用户得不到"请重新配对"的提示。
  2. 号码后缀匹配是对称的：一个较短的授权号会授权所有以它结尾的更长号码（授权扩大）。
  3. 运行时依赖没有打进产物。`dsh plugin add` 以 `link:` 方式安装时不会装插件自己的依赖，宿主启动直接报 `Cannot find package 'gmessages'`。本机 8 月 29 日的日志里实际发生过两次，后来是手工往 vendor 目录装依赖修好的，但根因没有消除。
- **一个中等 UX 缺陷未修，排进 M1：** 配对 RPC 会一直阻塞到手机确认为止，而浏览器端在有 pending 操作时停止轮询，所以校验码从来不会显示、Cancel 按钮不可点。UI 测试能通过，是因为 mock 直接返回了宿主在调用过程中不可能给出的 `pairing` 状态。
- **两个空白：** `DshSmsService`（`src/index.ts`，438 行编排层）零测试；插件从不写日志，错误提示却让用户"查看 host logs"。本次补了脱敏诊断日志，服务层测试排进 M1。

## 评审范围与方法

- 查本机运行态：`~/.dsh/profiles/web`（插件以 `link:` 挂在 `~/.dsh/vendor/dsh-sms-0.1.0`）、`~/.dsh/logs/web-supervisor.log`。
- 实跑：`npm test`、`npm run build`、`npm run audit:prod`、`npm pack --dry-run`、`DSH_BIN=~/.local/bin/dsh npm run test:profile`（rc.8）。

## 值得保持的设计

- **精确 turn 关联**（`turn-correlation.ts`）：用 `UserMessage.id` → claimed turn 绑定，浏览器里的活动不会串成短信回复。
- **交互代理 fail-closed**（`interactions.ts`）：交付不健康或投递失败就解析为 `unavailable`/取消，从不悬挂 agent。
- **凭据纪律**：会话文档只进 credential store；cookie 用完即弃；rotation 单写者；乐观 revision 写入失败时回滚凭据。
- **短信友好输出**：Markdown → 纯文本，代码块原样保留，按字形簇分块。
- **CI 真的装一次**：打包后装进一次性 web profile 并跑 `--help`，能抓到 manifest/bundle 级别的问题。
